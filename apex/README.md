# DG — Oracle schema and APEX application

Oracle AI Database 26ai, same instance as NIB, **own schema and own workspace**.
Nothing in this folder refers to the NIB schema, and nothing there refers to this.

The model follows the NIB org-structure design (scenarios, stable codes, the
hierarchy-chart plugin) but is written fresh for DG. Nothing was copied from
the NIB application: that application also carries finance, payments, sanctions
screening and DMS, plus bank-specific users, colours and data.

## 1. One-time setup (instance administrator)

1. Create the schema, e.g. `DG`, with quota on its tablespace.
2. In APEX administration, create the workspace `DG` on schema `DG`.
3. Only if you will run scripts over ORDS, as NIB does: REST-enable the
   schema, and configure `tools/ords-mcp` from the NIB repo with DG's own
   URL and credentials. Never reuse the NIB ones.
4. Install the hierarchy-chart plugin (`COM.APEXHIERARCHYCHART.PLUGIN`) into
   the new application. It is the same plugin as NIB, exported from there.

## 2. Install

From this folder, connected as `DG`:

```
@install.sql
```

It runs the five schema scripts, loads the 27/10 batch, and finishes with a
validation query that should return no rows. Every file is rerunnable.

| File | Contents |
|---|---|
| `01_tables.sql` | 13 tables: `ORG_*` structure, `JD_*` cards, `DG_*` batches and staff counts |
| `02_triggers.sql` | audit columns only |
| `03_lookups.sql` | unit types, link methods, classes, qualification levels, effort types |
| `04_views.sql` | two chart views for the plugin, the card view, the review queue, staff by unit |
| `05_package.sql` | `ORG_SCENARIO_PKG.CLONE_SCENARIO` and `VALIDATE` |
| `data/<batch>_NN_*.sql` | generated by `tools/gen_load_sql.py`, not edited by hand |

## 3. The model in short

- **`ORG_SCENARIO`**: one structure. Today there is `DG_ASIS_CARDS`, the
  structure as the cards describe it. A restructuring starts with
  `org_scenario_pkg.clone_scenario` and is edited as a separate tree. Codes are
  kept, so the two can be compared box by box.
- **`ORG_UNIT`**: المحافظة › أمانة السر / مديرية › قسم/فرع › دائرة › شعبة › مكتب/ورشة/غرفة.
  `BYLAWS_ARTICLE` ties each directorate to its article. The 2020 reconstruction
  directorate is marked `DRAFT_DECISION`.
- **`JD_CARD`, `JD_CARD_TASK`**: the cards. Every field is kept as written
  (`*_RAW`, `LOC_*`, `SUPERVISOR_RAW`) next to its normalised code, and every
  card points to its batch, file and position in the file.
- **`ORG_POSITION`**: one per card, plus a placeholder for each unit that other
  cards refer to but that has no head card. `LINK_METHOD_CODE` records how the
  supervisor was found, and its confidence (`STATED` / `APPROXIMATE` /
  `INFERRED` / `NONE`) feeds the review queue and the chart colours.
- **Scenario consistency** is enforced by composite foreign keys: a parent unit
  or a supervisor must be in the same scenario.

## 4. The application — first pages

| Page | Content | Source |
|---|---|---|
| Home | counts, cards by class and qualification, staff by unit | `jd_v_card`, `dg_v_staff_by_unit` |
| الهيكل التنظيمي | units chart, scenario selector | `org_v_chart_unit` |
| الهيكل الوظيفي | positions chart; amber = inferred line, red = no card | `org_v_chart_position` |
| بطاقات الوصف | searchable list by directorate, class, qualification | `jd_v_card` |
| البطاقة | one card as a form, its tasks as an editable grid, status workflow | `jd_card`, `jd_card_task` |
| المراجعة | the 102 items to confirm with DG, with a fix action for each | `org_v_review` |
| السيناريوهات | list, clone, validate | `org_scenario`, `org_scenario_pkg` |

The chart regions use the same plugin settings as NIB pages 10–11. The column
names in the views (`ID`, `PARENTID`, `EMPLOYEENAME`, `POSITIONNAME`,
`OFFICE`, `DESCRIPTION`, `CATEGORY_COLOR`) are the ones it expects. Filter on
`:P_SCENARIO_ID`.

## 5. Loading the next batch

```
tools/convert.sh incoming/<date> <work>
python3 tools/build_hierarchy.py <work>/docx analysis/unit_map.csv analysis/<date>_hierarchy.xlsx
python3 tools/gen_load_sql.py analysis/<date>_hierarchy.json analysis/unit_map.csv <staff.xlsx> <date> apex/data
```

Before generating, review `analysis/unit_map.csv` (directorates and staff rows)
and `analysis/unit_aliases.csv` (spelling variants of the same unit). Both are
maintained by hand on purpose: a wrong automatic match would be invisible.
